# Validation

## Automated, keyless checks

`npm test` exercises configuration resolution, bounded layout validation, text file operations and confinement, native completion/error projection, and sketch response validation with explicitly mocked provider responses. `npm run check` scans Git's publish candidate set for private runtime files, recognized credential patterns and personal deployment paths, and checks JavaScript syntax. This scanner is a project-specific guard, not a complete secret-detection product.

## Initial prototype integration evidence

Before repository packaging, a Linux ARM64 deployment using the revisions in `THIRD_PARTY_NOTICES.md` completed these real-model checks with `deepseek-flash`:

- All four actual CLIs responded to a shared prompt and recovered a marker in a second native-session turn.
- All four used tools to create and read back an independently checked workspace file.
- Cancelling a run removed all four owned containers.
- Browser checks exercised file create/edit/attach, drawing a component, layout save/reload and reconnecting during a running task.
- A real vision request converted two drawn regions into chat/files components. Recognition and adoption left the saved layout unchanged; explicit save survived reload. A separately injected HTTP error preserved the layout.

The original deployment used its own runtime image. Private traces, prompts, access credentials and exact deployment paths are not included in the public repository. No comparative success-rate or generalization claim follows from these smoke tests.

## Repository packaging checks

Eight keyless tests passed on both Windows/Node 24 and Linux ARM64/Node 24. The candidate-file release check passed on both systems. The generic Dockerfile built successfully on Linux ARM64. A separate DSH profile launched through `scripts/start.mjs` using configuration generated by `scripts/configure.mjs`; its DSH lane used the newly built image to create a file, read it back, and return a verified completion. The workspace contents were independently checked.

That integration reused the already installed pinned harness runtimes. It did not rerun the complete dependency installer on a fresh machine, did not validate every harness on the new image, and did not test Linux x64 execution. These checks must not be described as an automated fresh-install guarantee. CI's keyless checks are separately visible on GitHub after publication.

## Version 0.3 showcase checks

Eleven keyless tests pass on Windows/Node 24. Added coverage includes admitted-request accounting, native output truncation, workspace read leases, immutable snapshots, confinement, expiry and byte-range responses.

A Linux ARM64 deployment broadcast one self-contained interactive galaxy task to the four actual CLIs using DeepSeek Flash. All four produced HTML files that rendered in the Studio sandbox. Browser automation exercised pause/resume and speed controls in every pane without script errors. This was an iterative integration exercise: Claude reached the 900-second limit during screenshot auditing, then resumed in the same native session to report its existing artifact; Codex received a follow-up to fix a canvas stacking defect. The original failure and follow-up history remain visible. This is not a single-pass success claim or a latency benchmark.

A separate real DSH run generated a 6-second, 640x360, 24 fps H.264/yuv420p MP4. Independent ffprobe inspection and browser playback/seeking passed. A one-request budget test stopped at exactly one admitted request, rejected once without retrying, retained its file and resumed in the same native DSH session. Old failure history remained visible after service upgrade.

Browser checks confirmed inline HTML interaction while blocking parent DOM, browser storage and fetch access. Presentation mode, expansion and return controls passed. The updated Ubuntu ARM64 runtime image built with media tools and Chromium shared-library dependencies; an existing mounted Chromium headless binary launched successfully as a non-root user against a read-only root filesystem. Browser binaries themselves are not preinstalled by this Dockerfile. Private deployment traces and credentials are excluded from this repository.

After deploying the final image with browser shared libraries, all four native CLIs completed a short create/read-back task on that image. The host independently checked each resulting file. The final production page passed the four-pane interaction, direct-link, cumulative-metric and retained-failure checks.

## Unreleased model-case service

Eighteen JavaScript unit tests and three Python numerical tests pass locally. The model-case registry tests cover atomic duplicate rejection, mutation isolation, invalid measurements, catalog versions and disposal. `scripts/check-cordis-plugin.mjs` exercises actual plugin load/unload and provider replacement against the pinned DSH Cordis runtime; the dependent consumer re-registers on the replacement service. A separate full DSH web profile exposed six built-ins plus the example case through the authenticated HTTP API and closed its listener on disposal. The host check used a non-live key and made no model calls. The example ring is not part of the six-case modeling performance results.

## Unreleased deployment diagnostics

Twenty-eight JavaScript tests and three Python tests pass on Windows/Node 24 and Linux ARM64/Node 24. Added regressions cover canonical runtime aliases (including dangling parents), data/runtime overlap, key-file metadata, rejection before credential provisioning, no overwrite of existing keys, direct-overlay scalar limits and diagnostic output containment. The doctor passed against an existing resolved host configuration, and returned a failing image check for a deliberately nonexistent digest. Neither diagnostic started a model or container. A separate fake-key DSH profile loaded the plugin and consumer, served seven cases, enforced authentication and closed its listener when stopped. These preflight checks do not validate API credentials or prove every native harness operation.
