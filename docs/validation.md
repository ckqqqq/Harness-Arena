# Validation

## Automated, keyless checks

`npm test` exercises configuration resolution, bounded layout validation, text file operations and confinement, native completion/error projection, and sketch response validation with explicitly mocked provider responses. `npm run check` scans Git's publish candidate set for private runtime files, recognized credential patterns and personal deployment paths, and checks JavaScript syntax. This scanner is a project-specific guard, not a complete secret-detection product.

## Initial prototype integration evidence

Before repository packaging, a Linux ARM64 deployment using the revisions in `THIRD_PARTY_NOTICES.md` completed these real-model checks with `deepseek-flash`:

- All four actual CLIs responded to a shared prompt and recovered a marker in a second native-session turn.
- All four used tools to create and read back an independently checked workspace file.
- Cancelling a run removed all four owned containers.
- Browser checks exercised file create/edit/attach, drawing a component, layout save/reload and reconnecting during a running task.
- A real vision request converted two drawn regions into chat/files components. Recognition and adoption left the saved layout unchanged; explicit save survived reload. A separately injected HTTP error preserved the layout.

The original deployment used its own runtime image. Private traces, prompts, access credentials and exact deployment paths are not included in the public repository. No comparative success-rate or generalization claim follows from these smoke tests.

## Repository packaging checks

Eight keyless tests passed on both Windows/Node 24 and Linux ARM64/Node 24. The candidate-file release check passed on both systems. The generic Dockerfile built successfully on Linux ARM64. A separate DSH profile launched through `scripts/start.mjs` using configuration generated by `scripts/configure.mjs`; its DSH lane used the newly built image to create a file, read it back, and return a verified completion. The workspace contents were independently checked.

That integration reused the already installed pinned harness runtimes. It did not rerun the complete dependency installer on a fresh machine, did not validate every harness on the new image, and did not test Linux x64 execution. These checks must not be described as an automated fresh-install guarantee. CI's keyless checks are separately visible on GitHub after publication.
